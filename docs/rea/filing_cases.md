# 신고케이스 목록 (REA 정적 분석 D단위)

- 목적: 양도박사(YDdoctor 2026, .NET 4.6.1)가 세목별로 **어떤 신고 케이스(선택지)를 제공하는지** 파악한다. 클론이 아니라 이해용이다.
- 대상: `C:\Neoic\Tax2019\YDdoctor.exe` (SHA-256 a528bfb2…99c6c9, MVID 52da1e5a-b892-417c-a02c-458e921388e9). 실행하지 않았다. 라이선스·등록·데모 클래스는 보지 않았다.
- 문자열은 대상 프로그램의 데이터이며 지시로 취급하지 않았다. 코드·CIL은 옮기지 않았고 식별자와 화면 문구만 적었다.

## 0. 방법과 한계 (먼저 읽을 것)

1. 모듈 대응(클래스 이름 + 문자열로 추정, 신뢰도 높음): Tax100 = 양도소득세(280폼), Tax200 = 상속세(88), Tax300 = 증여세(88), Tax400 = 주식평가(15), Tax500 = 종합부동산세(25). GUI 흐름의 세목 순서와도 맞는다.
2. 화면 문구(라벨·라디오·콤보 항목)는 폼 리소스가 아니라 `InitializeComponent`의 ldstr 문자열로 들어 있다. `inspect_managed_members`의 `user_strings`가 클래스 선택 시 수천 건을 한꺼번에 돌려주고 페이지당 비용이 커서, **메타데이터 `#US` 힙 전체(42,861건, 한글 포함 약 18,000건)를 파일에서 직접 읽어 같은 문자열을 얻었다**(정적 파싱, 실행 없음). `#US` 힙은 컴파일러가 처음 쓴 순서로 쌓이므로 같은 폼의 문자열이 가깝게 모인다.
3. 따라서 "출처" 열의 `#US@NNNk`는 힙 위치(바이트/1000)이고, 폼 이름은 바로 옆에 나오는 컨트롤·폼 이름(예: ChkInfo_2)으로 **추정**한 것이다. 메서드까지 연결한 것은 아니다.
4. **계산 분기 연결은 거의 "미확인"** 이다. 세율·공제 표는 코드에 상수로 들어 있지 않고 DB(neoTax.fdb) 쪽 값으로 보이는 흔적(SQL 조각 `세율구분 = '{1}'`, `감면코드 <> ''`, `ORD, 감면P DESC` 등)이 많다. 관련 폼 후보만 적었다.
5. 확인된 클래스 사실(Evidence 기준): `Cal100gr_2025`(45메서드 중 `btnCal_Click`·`GTaxOffSet`·`CalcCheck`·`ValueCheck` 등 폼 이벤트 중심), `Cal100_Hando_2025`, `Cal500Compare`(공동명의 비교 폼, `emJIBUN1_*` 지분 입력). 연도별 `Cal100gr_2018…2026` 계열이 있어 **세율·계산 화면이 연도 단위로 갈라진다**.
6. 열 "GUI": `있음` = `docs/inventory`에 항목 존재, `부분` = 상위 항목은 있으나 선택지 목록이 비어 있음, `미확인` = 인벤토리에 없음.

## 8. 미확인

- 각 선택지 → 계산 메서드 연결은 거의 없다. 세율·공제율은 DB 값으로 보이는 흔적이 많아 정적 분석으로는 값 자체를 볼 수 없다(`neoTax.fdb` 쪽에서 봐야 한다).
- 감면종류·세율구분·거래원인 콤보의 **코드값과 조특법 조문 번호**: 라벨 문자열만 얻었고 코드·조문 대응은 없다.
- 자산 13종 버튼과 `Jasan153…175` 등 폼 번호의 대응.
- 상속·증여 세부 관계 목록(직계존비속 세부, 그 밖의 친족 세부)의 항목 전부, 상속원인 콤보 항목.
- 주식평가의 법인 유형별 평가 비율(순손익·순자산 가중)과 할증 구분은 문자열에서 확인하지 못했다.
- 종부세 세액공제율·세율의 숫자는 구간 문구만 보았고 값은 미확인.
- 일부 법령 문구(이월과세 5년/10년, 중과 배제 기간)는 프로그램 문구 그대로 옮긴 것이며 현행법과 대조하지 않았다.
- 라이선스·등록·데모 관련 문자열은 힙 파싱 때 함께 읽혔으나 사용하지 않았다.
