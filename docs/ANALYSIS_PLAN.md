# 양도박사 분석 계획 (블랙박스 + 오라클)

> 목적: 양도박사(레거시)를 **관찰**해서 새 양도세 신고 프로그램의 데이터 모델·출력 규격·검증 데이터를 확보한다.
> 계산 로직의 기준은 양도박사가 아니라 **소득세법 §94~§118, 시행령·시행규칙, 국세청 전자신고 파일 명세**다.
> 양도박사는 "실무자가 어떤 순서로 무엇을 입력하는가"와 "정답 비교용 오라클"로만 쓴다.

## 0. 원칙

| 구분 | 내용 |
|---|---|
| 주 분석 대상 | **설치형** (로컬 DB, 전자신고 파일, 오프라인 반복 실험, 버전 고정) |
| 보조 분석 대상 | **클라우드형** (최신 세법 반영 상태, 현재 UX 기준선) |
| 허용 | 입력→출력 관찰, 화면 캡처, 본인이 만든 저장 파일·전자신고 파일·출력물 분석 |
| 금지 | 디컴파일, 실행파일 코드 추출, 클라우드 자동화·스크래핑 (저작권법 §101조의4, EULA) |
| 보고 주기 | **입력 화면 1개 또는 신고서 1종을 한 바퀴 다 돌 때마다** 현황을 정리해 사용자에게 알린다 |

## 1. 폴더 구조

```
baksa/
├─ docs/
│  ├─ ANALYSIS_PLAN.md        ← 이 문서
│  ├─ screens/                ← 화면 캡처 (NN_화면명.png, 순서 번호)
│  ├─ steps/                  ← psr.exe 기록 (.zip/.mht)
│  ├─ inventory/              ← 화면별 입력 항목 인벤토리 (screen_NN.md)
│  └─ reports/                ← 단계별 진행 보고
├─ data/
│  ├─ raw/                    ← 양도박사가 만든 원본 파일 (읽기 전용 사본)
│  ├─ schema/                 ← DB 스키마 추출 결과
│  └─ efile/                  ← 전자신고 파일 샘플
├─ cases/                     ← 테스트 케이스 (입력값 + 양도박사 산출값)
└─ tools/                     ← 분석용 Python 스크립트
```

## 2. 단계별 계획

### 1단계. 입력 흐름 캡처 (화면별 입력 항목 인벤토리)

- **Windows 단계 레코더 (`psr.exe`)**: 클릭할 때마다 스크린샷과 설명이 자동으로 기록된다. 신고 1건을 처음부터 끝까지 입력하며 기록한 뒤 `docs/steps/`에 저장한다.
  - 참고: Windows 11에서 사용 중단(deprecated) 예정인 도구다. 현재 PC에는 있지만 나중에 사라질 수 있으니 결과물을 바로 보관한다.
- **보조 스크린샷**: `docs/screens/NN_화면명.png` 형식으로 화면 순서대로 번호를 붙인다.
- **산출물**: `docs/inventory/screen_NN.md`

  | 항목명 | 타입 | 필수 | 선택지/형식 | 조건부 노출 | 근거 조문 | 비고 |
  |---|---|---|---|---|---|---|

- ✅ 체크포인트: 화면 하나의 인벤토리가 끝날 때마다 보고한다.

### 2단계. 로컬 데이터 파일 분석

1. **Process Monitor**(Sysinternals)에서 양도박사 프로세스로 필터를 걸고 `WriteFile` / `CreateFile`을 기록한다. 저장 버튼을 누를 때 어떤 파일을 쓰는지 찾는다.
2. 찾은 파일은 `data/raw/`에 **복사본**으로 옮긴 뒤 분석한다. 원본은 건드리지 않는다.
3. 형식별 도구 (Windows 기준):

| 형식 | 도구 |
|---|---|
| Access `.mdb` / `.accdb` | Python `pyodbc` + 설치된 64비트 *Microsoft Access Driver*, 또는 WSL에서 `mdb-schema` / `mdb-export` (mdbtools) |
| dBASE `.dbf` | Python `dbfread`, 또는 설치된 *Access dBASE Driver* |
| SQLite | DB Browser for SQLite, Python `sqlite3` |
| Firebird / MSSQL LocalDB | DBeaver |
| 형식을 알 수 없음 | WSL `file` 명령 + **HxD**(Windows 무료 헥스 에디터)로 매직 바이트 확인 |

- **산출물**: `data/schema/` 아래에 테이블·컬럼 목록을 둔다. 이것이 **데이터 모델 초안**이다.
- 1단계 인벤토리와 맞대 보며 "화면 항목 ↔ DB 컬럼" 매핑표를 만든다.
- ✅ 체크포인트: 스키마 추출과 매핑이 끝나면 보고한다.

### 3단계. 전자신고 파일 · 출력 서식

- **전자신고 파일**: 보통 고정폭 텍스트다. 국세청 "양도소득세 전자신고 파일 작성 명세"를 기준 문서로 삼고, `tools/`의 Python 스크립트(슬라이싱, `struct`)로 파싱해 필드 매핑을 만든다.
  → **이 명세가 새 프로그램이 지켜야 할 실제 출력 규격이다.**
- **인쇄 신고서**: PDF 프린터로 저장한 뒤 `pdfplumber`로 항목 위치와 라벨을 추출한다. 신고서 종류(양도소득과세표준신고서, 계산명세서, 부속서류 등)마다 따로 정리한다.
- ✅ 체크포인트: 신고서 1종을 끝낼 때마다 보고한다.

### 4단계. 계산 로직 검증 (오라클)

- 디컴파일하지 않고 **케이스 실험**으로 검증한다.
- `cases/`에 케이스별 입력값과 양도박사 산출값을 기록한다(CSV/스프레드시트).
- 우선 다룰 케이스:
  - 1세대1주택 비과세, 고가주택 안분
  - 다주택 중과 (유예기간 포함)
  - 장기보유특별공제 (일반 / 1세대1주택 보유·거주 구간)
  - 상속·증여 취득가액, 환산취득가액, 이월과세
  - 분양권·입주권, 단기양도 세율
  - 감면 (조특법), 예정신고 / 확정신고 합산
- **Python으로 세법 기준 계산기를 따로 짜서** 양도박사 결과와 비교한다.
  - 결과가 다르면 법령을 기준으로 원인을 판정한다. 양도박사 오류일 수도 있고, 숨은 분기일 수도 있고, 내 해석이 틀렸을 수도 있다.
  - 이 방식이 코드를 역분석하는 것보다 정확하고, 결과물이 그대로 새 프로그램의 **회귀 테스트 세트**가 된다.
- 참고: `~/v/taxflow`는 현재 PC에 없다. 재활용할 기존 코드가 다른 곳에 있다면 경로를 알려주면 된다.
- ✅ 체크포인트: 케이스 그룹(예: 장특공제) 하나를 끝낼 때마다 보고한다.

### 5단계. 클라우드형 (보조)

- 브라우저 DevTools의 Network 탭에서 저장·계산 요청의 JSON 바디를 확인한다. 이것으로 데이터 모델을 교차 검증할 수 있다. HAR로 내보내 `data/raw/cloud/`에 보관한다.
- 설치형과 비교할 것: 세법 반영 버전 차이, 화면 흐름 차이, 추가된 기능.
- **본인 계정으로 직접 조작하며 관찰만 한다.** 자동화나 스크래핑은 하지 않는다.

### 6단계. 불편한 점 수집 → 업그레이드 포인트

- 분석하면서 느낀 불편함을 `docs/reports/pain_points.md`에 계속 쌓는다(중복 입력, 숨은 메뉴, 오류 메시지 품질 등).
- 가능하면 세무사 사무실 실사용자 인터뷰도 한다.
- 후보 기능: 홈택스 연동, 시나리오 자동 비교, 절세 시뮬레이션, AI 서류 인식(등기부·매매계약서).

## 3. 최종 산출물 → 새 프로그램 설계 입력

| 분석 산출물 | 새 프로그램에서의 용도 |
|---|---|
| 화면 인벤토리 + DB 스키마 | 데이터 모델 / 입력 UX 설계 |
| 전자신고 파일 매핑 | 출력 모듈 규격 |
| 케이스 세트 (입력 + 정답) | 계산 엔진 회귀 테스트 |
| 세법 기준 계산기 | 조문 단위로 규칙을 모듈화한 엔진의 프로토타입 |
| 불편한 점 목록 | 차별화 기능 우선순위 |
